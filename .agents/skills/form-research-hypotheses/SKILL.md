# Формирование исследовательских гипотез

В конце серии преврати результаты в набор проверок, по которым можно принять решение. Серией считай связанные эксперименты, после которых меняется приоритет, исчерпывается выбранный подход или пора проверить переносимость. Используй [журнал](../../../docs/experiments.md), [отчёт версии](../../../docs/metrics/AGENTS.md) и по возможности сырые пары ответов. При активном исследовании передай выбранный пилот в [run-agent-eval](../run-agent-eval/SKILL.md).

## Разбери, что изменилось

- Восстанови для сравниваемых прогонов версию, контроль, знаменатель, срез и измеряемое действие. Сопоставь пары по ID, посчитай победы и потери, отметь повторяющиеся документы и отсутствующие измерения. Отдельно разберись со сбоями провайдера, формы ответа и оценщика.
- Выдели пользовательский исход и промежуточные сигналы. Для ответа с источниками проверь цепочку «релевантный URL → применимая выдержка → верный факт → подтверждающая цитата». Для маршрутизатора считай отдельно точность действия и исход после его исполнения. При расхождении вернись к конкретным ответам и источникам. [Microsoft Research о трактовке метрик](https://www.microsoft.com/en-us/research/publication/a-dirty-dozen-twelve-common-metric-interpretation-pitfalls-in-online-controlled-experiments/).
- Проверь предел подхода по имеющимся данным. Например, для выбора между сниппетом и чтением посчитай, на скольких кейсах строгий зачёт есть хотя бы в одной сохранённой ветке. Такой результат ограничен версиями веток, срезом и оценщиком. Если выигрыш отсутствует в самих ветках, приоритет получает новое действие или другая реализация существующего действия.
- Сформулируй альтернативное объяснение каждого результата, от которого зависит решение. Например, рост зачётов может идти от доказательств, а может от меньшего числа невалидных вердиктов. Выбери наблюдение, которое позволит различить причины.

## Ищи механизмы во внешних источниках

- В каждой серии сделай короткий поиск по типу сбоя или цели, даже если в журнале уже есть идеи. Ищи воспроизводимые работы, официальную документацию, публичный код и инженерные разборы авторов систем. Смотри соседние задачи, где уже решают похожую проблему. Например, для лишних вызовов проверь выборочное извлечение, каскады и маршрутизацию моделей.
- Для идеи из источника запиши, какой механизм переносим, что в источнике реально измерили и чем наши входы, ограничения и метрики отличаются. Провайдерская документация подтверждает контракт API. Выигрыш в качестве, цене и задержке проверь на своём eval. Если результатов воспроизведения мало, отметь это и сохрани идею для короткого пилота при ясном механизме и дешёвом контроле.
- При сопоставимой цене проверки начни с воспроизводимого подхода, подходящего под наш сбой. Используй его как контроль для нового метода. Порядок можно изменить, если дешёвый тест нового метода быстрее покажет, стоит ли продолжать. Зафиксируй причину.
- Для новых API преврати свойства интерфейса в отдельные гипотезы. Например, у Jev можно проверить выбор из допустимых действий, несколько независимых проверок за один запрос или использование уверенности для дорогостоящего повтора. Для уверенности измерь ошибки на своём срезе перед выбором порога. Сравни с правилом и обычной моделью со структурированным ответом при одном наборе входов и действий. [RouterAI Decisions](https://routerai.ru/docs/guides/overview/decisions/overview)

## Сформируй и упорядочь варианты

Из опорных наблюдений выведи варианты с разными причинными механизмами. Проверь, какой сигнал можно получить на соседнем этапе и какое допущение исходной схемы стоит оспорить. Если локальные правки перестали переноситься, рассмотрение более крупного изменения особенно уместно. Для агента это может быть замена действия «читать первый URL» на выбор цели чтения, уточнённый поиск или вопрос пользователю. Для стоимости и задержки рассмотри кэш, повтор, модель, объём входа и критический путь. Выбирай только варианты, за которыми стоят конкретные ошибки, измеримые расходы или обнаруженный пробел.

Для каждой идеи добавь запись в очередь журнала с этими полями:

| Поле | Что записать |
| --- | --- |
| Наблюдение | ID эксперимента или кейса, абсолютные числа и знаменатель, связанный сбой |
| Гипотеза | Какое изменение через какой механизм должно сдвинуть какой исход и на каких кейсах |
| Проверка | Контроль, изменение, фиксированные условия, срез и самый дешёвый способ получить различимый результат |
| Решение | Основная метрика, порог успеха и допустимые потери. Для затронутых этапов зафиксируй ограничения по качеству, времени, цене и сложности эксплуатации |
| Риск и основание | Альтернативное объяснение, переносимость и сила доказательств. Для внешней идеи дай прямую ссылку, укажи применимый механизм и локальную проверку |

Приоритизируй по масштабу обнаруженного сбоя, силе основания, цене проверки и тому, изменит ли ответ следующее решение. Оценку потенциального эффекта помечай как оценку. Для сложного изменения укажи, какие дополнительные инструменты, хранение и эксплуатация понадобятся. Источник нужен для механизма, который он действительно объясняет. [Microsoft Research о дизайне экспериментов](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-pre-experiment-stage/).

## Спроектируй следующую серию

- Начни с анализа архива или проверки при готовых доказательствах, если этого достаточно. Если требуется живой прогон, зафиксируй входы, конфигурацию, метрику, порог и бюджет до просмотра результата. Кейс, использованный для построения гипотезы, проверяет механизм. Для подтверждения возьми отдельные источники и вопросы. Включи контрольные успехи, которые можно потерять.
- Если гипотеза касается веб-поиска или чтения, держи документы и домены подтверждающего среза отдельно от настройки. Проверь, что правило работает с данными запроса и выдачи без эталонного URL или условия, завязанного на конкретный сайт. Отдельно просмотри результаты по основным вузам. Размер прогона выбирай по [правилу исследовательского цикла](../../../agent/AGENTS.md#исследовательский-цикл).
- Для совместимой пары правок с возможным взаимодействием сравни четыре ветки на одних кейсах: контроль, A, B, A+B. Сохрани общий лимит, если он важен для решения. Когда бюджет позволяет только проверку A+B, вывод относится к комбинации. [NIST о выборе экспериментального дизайна](https://itl.nist.gov/div898/handbook/pri/section3/pri33.htm).
- Для decision-модели проверь, может ли каждое предлагаемое действие улучшить ответ. Затем сравни простой способ выбора и модель с одинаковым набором действий и лимитом. Измерь точность решения, лишние действия, строгий зачёт и добавленные вызовы. Диагностический срез с искусственным балансом классов пометь явно.
- Выбери ближайший исполнимый пилот и запиши, какие результаты приведут к внедрению, подтверждающему прогону, смене механизма или закрытию гипотезы. Остальные варианты оставь с причинами приоритета. Обнови очередь после следующей серии по фактическим исходам.
