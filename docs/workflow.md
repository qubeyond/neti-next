# Рабочий процесс для агентов

Эта процедура определяет, где фиксировать намерение, решение, фактическую проверку и следующий шаг.

## Взять задачу

1. Свяжи задачу с этапом из [stages](stages.md) и требованием из [spec](spec.md). Для инфраструктурной работы можно указать ADR.
2. Зафиксируй результат, границы и критерии приёмки. Используй [шаблон передачи](tasks/template.md) для задач между агентами или сессиями.
3. Для параллельной работы используй отдельную ветку или worktree. Для общего контракта или конфига укажи пересечение и владельца решения.

## Внести изменение

- Изменение поведения привязывай к критерию приёмки в [spec](spec.md). Договорённость должна быть понятна сама по себе и проверяема на нормальном входе.
- При изменении сервисной границы, схемы данных, зависимости от внешней системы или выпуска записывай ADR. Для локального рефакторинга внутри действующего решения достаточно описания задачи.
- Для межсервисной правки используй [правила HTTP-контрактов](api-contracts.md).
- Пиши имена веток кратко, например `feat/agent/retrieval` или `fix/deploy/healthcheck`. Форма коммита — `тип(область): описание` с глаголом в прошедшем времени, например `feat(agent): добавлен поиск по базе`.

## Проверить и передать

1. Выполни нужные локальные проверки из [deploy/AGENTS.md](../deploy/AGENTS.md). Изменение поиска или ответа проверь на целевом срезе по [evals/AGENTS.md](../evals/AGENTS.md).
2. Сохрани команду, вход или срез, фактический результат и ограничения. Измерения записывай в [формате отчёта версии](metrics/AGENTS.md).
3. Обнови статус этапа и ссылки на доказательство приёмки. Передай незавершённый вопрос с указанием места в коде, текущего наблюдения и следующей проверки.
4. При порученной публикации проверь SSH-адрес `origin` и статус GitHub Actions. Публикация образов и активация на сервере проверяются отдельно.

## Провести изменение через GitHub

1. Обнови `origin/dev` и создай от него свою ветку. Публикуй только её.
2. Открой PR с базой `dev` и приложи фактически выполненные проверки. Если изменение требует обсуждения, держи PR в черновиках.
3. Когда PR готов и открыт из ветки участника этого репозитория, проверь статус `Dev auto-merge`. Он включает squash-слияние, которое ждёт `Checks` и оба Compose smoke.
4. После слияния обнови `origin/dev`. Следующую задачу начинай от новой версии `dev`.

## Вести архитектурные решения

- Записывай ADR в файле модуля-владельца из [индекса документов](AGENTS.md). Для влияния на соседний модуль дай ссылку на тот же ADR из его инструкции или решения.
- Указывай стабильный ID, дату, статус, контекст, решение, последствия и условие пересмотра. Сравни варианты, которые реально рассматривались.
- Используй статусы «предложено», «принято» и «заменено». При замене сохраняй причину и ссылку на следующую запись, чтобы агент мог восстановить ход решения.
