# ADR бэкенда

## BE-01 · Go и отдельная HTTP-граница

- **Дата и статус** — 2026-11-20, принято.
- **Контекст** — Пользователь выбрал Go для бэкенда и отдельный Python-рантайм для агента. Спецификация прикладного API ещё формируется.
- **Решение** — Бэкенд владеет `/api/…` и собственным Dockerfile. Начальная реализация содержит healthcheck на стандартной библиотеке Go. Интеграция с агентом проходит через договорённый HTTP-контракт.
- **Последствия** — Go может стартовать самостоятельно. Выбор хранилища, модель пользователей и контракты диалога открыты.
- **Пересмотр** — При проектировании первого прикладного маршрута закрепить ответственность сервиса, границы доступа и модель ошибок.

## BE-02 · Владелец истории диалога

- **Дата и статус** — 2026-11-20, заменено решением BE-03.
- **Контекст** — DIALOG-01 требует сохранять релевантную историю в рамках текущего диалога. Базовый режим агента работает с одним вопросом.
- **Вариант** — Go владеет диалогом, передаёт агенту нужную историю и хранит связанный с диалогом результат. Другой рассматриваемый вариант — клиент передаёт историю с запросом для первоначального демонстрационного сценария.
- **Открыто** — Где хранится история, как изолируются диалоги, требуется ли сохранение между сессиями и какой объём контекста получает агент.
- **Решение по этапу** — На ST-04 сравнить варианты по проверкам DIALOG-01 и закрепить формат запроса до реализации UI.

## BE-03 · Профили, диалоги и гостевое рабочее пространство

- **Дата и статус** — 2026-11-21, принято.
- **Контекст** — История, файлы и настройки должны сохраняться между запусками для профиля и изолироваться по владельцу. Гостевые чаты должны исчезать после обновления страницы или выхода из режима.
- **Решение** — Go владеет профилем, авторизацией, диалогом и файлами. BoltDB хранит данные профиля и файлы в одной транзакционной базе одного экземпляра. Гостевой токен живёт в памяти вкладки, а данные гостя — в памяти Go. Состояние сообщений читается по HTTP, WebSocket уведомляет об изменениях. Структура будущего входа агента и текущий переход описаны в [задаче](../tasks/workspace.md).
- **Альтернативы** — Хранение диалога в браузере усложняет изоляцию и восстановление профиля. Отдельная база и объектное хранилище позволят запустить больше процессов, но требуют дополнительной инфраструктуры.
- **Пересмотр** — При запуске нескольких экземпляров Go вынести состояние, вложения и обмен событиями в общую инфраструктуру и проверить миграцию.

## BE-04 · PostgreSQL и владение данными

- **Решение** — одна база `neti`. Go подключается как `neti_backend` и работает с профилями, диалогами, сессиями и вложениями в `backend`. Агент подключается как `agent_cache` и работает с публичными документами в `document_cache`. Административные и сервисные пароли передаются раздельно. Тесты проверяют запрет обращения к чужой схеме даже по полному имени.
- **Импорт** — при старте Go читает старый BoltDB с постоянного тома в режиме чтения. Профили, диалоги, вложения, активные сессии и отметка миграции записываются в одной транзакции. Повторный старт пропускает завершённый импорт. Записи под незавершённой миграцией откатываются. Живой старый экземпляр Go нужно остановить перед импортом.
- **Переключение и откат** — до выкладки сделай резервную копию старого тома и запланируй окно переключения. Проверь вход, сохранённый диалог и вложение. Откат на старый образ безопасен до открытия записи пользователям. После записи в PostgreSQL откат на BoltDB требует переноса новых данных, иначе читается старый снимок. Старый том остаётся подключённым только для чтения.
- **Границы** — пользовательские данные остаются в Go, публичный кэш можно заново заполнить из веба. Гостевые сессии, активные ходы и уведомления остаются в памяти экземпляра Go. Переход на несколько реплик потребует отдельного решения по этим данным.
