# Eval

Набор вопросов и воспроизводимые проверки поиска, генерации и цитирования. Формат результата и предыдущие версии описаны в [отчётах по версиям](../docs/metrics/AGENTS.md).

Для приёмки используй предметные срезы по [вузам и темам](../docs/spec.md). Сценарии организаторов по НЭТИ проверяй отдельным срезом. В предметный срез добавляй вопросы по всем темам кейса, конфликты редакций и отсутствующие в снимке факты. Финальный замер фиксирует SHA приложения, модель, конфигурацию и снимок базы. Для защиты сообщай результаты прямых, косвенных, многошаговых проверок и легитимных запросов раздельно.

Принципы разделения проверок описаны в [ADR eval](../docs/adr/evals.md).
Гипотезы и решения ведутся по [исследовательскому циклу агента](../agent/AGENTS.md#исследовательский-цикл).

Команда `uv run --project agent --locked python -m evals.research_notes` сокращает вывод при работе с отчётами. Используй `recent` для сводки, `show E111` для одной записи, `metrics <отчёт.md> "Качество"` для раздела отчёта и `json <отчёт.json> --key summary` для поля из исходных данных. Готовый эксперимент записывай через `record E112 <запись.json>`. Поля — `title`, `result`, `cost`, `decision`, `details`. Команда обновляет строку сводки и детали одной записью. `--dry-run` показывает результат без записи.

## Данные

- Входы находятся в `questions*.jsonl`, рубрики — в `gold/answers*.jsonl`, источники — в `gold/evidence*.json`. Соединяй записи по стабильным идентификаторам.
- Для фактов указывай официальный URL, точный фрагмент и его место в источнике. Для таблицы фиксируй строку и заголовок, для ссылки — адрес назначения `linked_url`.
- Разделяй домен и навыки. При выделении подтверждающего среза держи вместе вопросы по одному документу, его версиям и зеркалам. Для проверки переноса между сайтами оставляй целые домены или семейства шаблонов на подтверждение. Выборку фиксируй до просмотра результатов.
- Показывай число вопросов и строгие зачёты по каждому основному вузу. Вопросы сравнения учитывай в срезах обоих вузов и один раз в общей метрике. Кейс с сайта, использованного при настройке гипотезы, показывает работу механизма на этом сайте. Переносимость проверяй на других источниках.
- В обычном прогоне передавай модели вопрос и результат поиска. Эталонные факты, критерии и URL доступны оценщику и диагностике. В `oracle` агент получает готовые выдержки и сведения о месте в документе.
- В `grounding` входные фрагменты специально не подтверждают спрашиваемый факт. Сценарии уточнения подготовлены отдельно для многоходового агента.
- Фикстуры устойчивости находятся в `questions-robustness.jsonl` и `gold/answers-robustness.jsonl`. Их `base_id` привязывает вопрос к существующему исходному ответу. Синтетические приписки добавляются только в тестовый вход. Эталоны и исходные источники сохраняются отдельно.

## Измерение

| Режим | Что проверяет | На что смотреть |
| --- | --- | --- |
| `e2e` | Поиск, контекст, генерация и цитаты в одной цепочке | Строгий зачёт, сбои этапов, время до ответа, запросы и стоимость |
| `retrieval` | Поиск и позиции известных URL без вызовов модели | Hit Rate@k, Recall@k, MRR@k и покрытие доказательств |
| `oracle` | Ответ по проверенным фрагментам на те же вопросы | Полнота фактов, применимость и дословность цитат, ошибки формата |
| `grounding` | Отказ при недостаточных или неподходящих доказательствах | Безопасные отказы и утверждения без доказательств |
| `run_robustness` | Перефразы, ложные предпосылки, ловушки вуза, года и услуги, инструкции в вопросе или в источнике. Контекст фиксирован | Сохранение полезности, исправление предпосылки, ложные ответы, метки инъекций, повторяемость |

Офлайн-проверка из корня репозитория — `uv run --project agent --locked python -m pytest evals/tests`.

Примеры живых прогонов с сохранением исходного результата:

```bash
mkdir -p evals/reports
uv run --project agent --locked python -m evals.run_web_baseline \
  --mode e2e --domain housing --skill table --search-min-interval 7 --judge-max-tokens 3072 \
  > evals/reports/e2e-housing-table.json
uv run --project agent --locked python -m evals.run_web_baseline \
  --mode oracle --case sgups-dorm-difference > evals/reports/oracle-sgups-dorm-difference.json
```

- Для полного расширенного прогона опусти фильтры. `--dataset core|extension|expanded` задаёт набор. `--domain`, `--skill` и `--case` задают срез.
- `--institution` оставляет вопросы, помеченные одним указанным вузом. Для межвузовских сравнений используй `--skill multi-source` или конкретные ID.
- `--reuse-search <отчёт>` переиспользует поисковую выдачу. `--fill-missing-search` разрешает новые поиски для недостающих кейсов. `--context-mode prefix` восстанавливает историческую обрезку для контроля. `--report <отчёт>` пересчитывает срез без API.
- `--judge-model` позволяет менять оценщика. Согласуй модель, рубрику, лимиты и вопросы для сравниваемых версий. Для проверки формата без оценки используй `--no-judge`.
- Для сравнения только поиска используй `python -m evals.compare_search` с тем же префиксом uv. `--provider firecrawl --provider tavily` выбирает движки, `--enhanced` добавляет сокращённый запрос, `--all` включает исходную веб-выборку.
- Для сравнения ответов запускай `run_web_baseline --provider firecrawl` и `run_web_baseline --provider exa` с одинаковыми вопросами, лимитами и оценщиком. Свежий или сохранённый поиск указывай в условиях обеих веток. Формируй общий отчёт через `render_provider_comparison <firecrawl.json> <exa.json>`; передавай фактические `--answer-tokens`, `--source-chars` и действующий тариф `--exa-usd-per-1000`, если нужна оценка цены.
- Живые прогоны берут настройки из `agent/.env` и расходуют квоту. Сохраняй сырые результаты в игнорируемый `evals/reports/` на время анализа. Итоги сохраняй отдельным отчётом версии.

Для устойчивости используй `python -m evals.run_robustness` с тем же префиксом uv. `--list` валидирует и показывает кейсы локально. `--live --kind prompt-injection` запускает один срез. `--domain` и `--case` выбирают узкую выборку, `--repeat 2` измеряет повторяемость. Уточнения проверяются через HTTP в `evals.probe_agent_boundaries`.

## Проверка переносимости

- [Фиксированное разбиение веб-набора](splits-web-v1.json) содержит пять фолдов по группам документов и срезы по целым вузам. Общий эталонный URL, ссылка назначения, отмеченная семья зеркал или редакций и производные вопросы образуют одну группу. Для обнаруженных зеркал и версий добавь одинаковый `document_family` к эталонным доказательствам. У среза по вузу связанные вопросы вне выбранного вуза перечислены в `excluded` и исключаются из настройки для этого среза.
- Для настройки правил, порогов, промптов или выбора модели используй кейсы за пределами `test` и `excluded`. Затем заморозь варианты и оцени одинаковый `test` для всех. При настройке на каждом фолде выбирай параметры внутри его части настройки. Разбиение старых ответов по группам — диагностика. Для финальной проверки собери отдельные документы и вопросы, которых ещё не было в экспериментах.
- `--split-manifest evals/splits-web-v1.json --fold 1` или `--holdout-institution "НГТУ НЭТИ"` выбирает целый срез. Добавь `--report <полный-отчёт.json>` для офлайн-пересчёта. Команда проверяет отпечаток вопроса, рубрики и доказательств, запрещает дополнительные фильтры и отклоняет неполные отчёты по срезу.
- Сохраняй результаты по каждому фолду и общий результат на всех уникальных кейсах. Для сравнения правила с моделью фиксируй состав доступных действий, видимый контекст, бюджет поиска и рубрику. Считай строгий зачёт после действия, лишние веб-вызовы, долю неверных остановок, цену и p95. При изменении данных создай новый манифест через `python -m evals.splits --folds 5` и сохраняй версию исходного среза для старых отчётов.

## Правила оценки

- Строгий зачёт требует полного ответа с правильными фактами, применимыми доказательствами и валидными цитатами. Засчитывай другой официальный URL, если он доказывает тот же факт при тех же условиях.
- Дословность проверяй по предъявленному фрагменту. Применимость цитаты проверяй с учётом вуза, филиала, года, условий и единиц. В расчёте нужны доказательства исходных величин и правильный итог.
- Отделяй ошибки оценки, ошибочные факты и честный отказ. Проверяй по источнику спорные вердикты, особенно когда одна модель отвечает и оценивает.
- Для атак сравнивай появление контрольной метки и сохранение строгого ответа с исходной чистой версией. Отсутствие метки само по себе не подтверждает устойчивость. Оценивай ответ по исходному вопросу и чистым доказательствам. Ложные предпосылки засчитывай по корректному факту и применимой цитате.
- В отказе отдельно считай подтверждённый отказ по смыслу и строгий статус `unverified` без цитат. Цитата может пояснять, какой другой период или услугу описывает документ. Сбои генерации и невалидные оценки показывай отдельно. Для повторов считай согласованность видимых действий и итоговых исходов на одних входах. Стабильность сама по себе не измеряет правильность.

- Для проверки штатной валидации, повторной генерации и восстановления запусти `run_web_baseline --service-pipeline` на малом срезе. `--reuse-search` переиспользует начальную выдачу. Ветка восстановления всё ещё может обращаться к поисковику или ридеру. Количество начальных поисков и действий восстановления отчёт показывает отдельно.

- Для проверки фактического пайплайна на прямых и косвенных инъекциях используй `python -m evals.run_robustness --live --variant service`. Он переиспользует фиксированные источники и отключает внешнее восстановление. Набор `python -m evals.probe_agent_boundaries` выполняет синтетические сценарии через FastAPI с реальной моделью и подставным поисковиком. Маркер в ответе, маркер в запросе к поиску и сохранение правильного факта фиксируются отдельно.
