# NETI Next

Правила для агентов, которые работают с кодом, туллингом и инфраструктурой сервиса вопросов о вузах Новосибирска.

## Перед началом

- Проверь рабочую ветку, `git status --short` и существующие изменения. Прочитай ближайший `AGENTS.md` каждой затронутой папки.
- Для фичи или изменения контракта используй [рабочий процесс](docs/workflow.md). Для локальной правки достаточно инструкции сервиса и относящегося к задаче навыка.
- Для исследования качества агента используй [исследовательский цикл](agent/AGENTS.md#исследовательский-цикл).

## Границы

- Поддерживай единый репозиторий и общий запуск через Compose. Каждый сервис должен собираться командой Docker из собственной папки и запускаться независимо.
- Храни Dockerfile, код, зависимости и пример окружения в сервисе-владельце. Общие файлы запуска и настройки связки размещай в `deploy/`.
- Передавай данные между сервисами через публичные контракты. Приложения не импортируют код соседних сервисов. Eval импортирует пакет агента как инструмент проверки.
- Для HTTP используй `/api/…` для Go и `/agent/…` для FastAPI. Публичные изменения сверяй с [правилами HTTP-контрактов](docs/api-contracts.md). Проверки здоровья должны работать без внешних провайдеров.
- Новые абстракции, сервисы и зависимости добавляй под требования задачи. Следуй принятым инструментам языка.

## Оформление кода

- Имена переменных, функций и типов пиши по-английски и по назначению. Избегай сокращений, которые требуют догадок. Для пользовательских сообщений и документов используй русский.
- Python форматируй Ruff. Используй четыре пробела для отступов и две пустые строки между определениями верхнего уровня. Новый Python-модуль начинай с короткого докстринга по-русски о его назначении.
- Go форматируй `gofmt` с его табуляцией. В TypeScript, TSX, CSS, JSON и YAML придерживайся двух пробелов. В рецептах Makefile используй табуляцию.
- Отделяй логические блоки пустой строкой, если это помогает прочитать переход к следующему условию, шагу или результату. Для короткого связного выражения сохраняй компактность.
- Для Python агента и скриптов следуй `scripts/hooks/check_code_style.py`: смысл выражай именами, комментарии оставляй для служебных маркеров. В остальных языках комментарий может пояснять неочевидное ограничение или причину. Назначение параметра окружения при необходимости поясни одной строкой в шаблоне.
- Стабильные для приложения значения оставляй в коде. Повторяющиеся значения с общей семантикой оформляй как именованные константы. Адреса, ключи и параметры развёртывания храни в конфигурации владельца.
- Разделяй файлы по смыслу и фактическим границам модуля. Markdown-файлы называй строчными буквами через дефис, сохраняя общепринятые имена `README.md`, `AGENTS.md` и `SKILL.md`.

## Конфигурация и безопасность

- Клади настройки сервиса в его `.env.example`, а параметры оркестрации — в `deploy/.env.example`. Сохраняй рабочий `.env` при повторном запуске. Документируй новое значение в шаблоне владельца.
- Секреты модели и поисковика доступны только агенту. Храни их вне Git и образов, не выводи в логи, отчёты, ответы API и клиентскую сборку.
- На границе HTTP валидируй данные и возвращай понятные ошибки. Тексты из выдачи рассматривай как внешние данные. Избегай пересылки пользовательских данных в диагностические отчёты.
- Офлайн-тесты используют подстановки. Живые запросы к модели и поиск запускай в рамках согласованной задачи и учитывай расход квоты.

## Проверки и Git

- Для правки одного сервиса начни с его локальных проверок. Для общих конфигов и изменений, затрагивающих несколько сервисов, запусти `make -C deploy check`. Для Docker и прокси добавь `make -C deploy smoke`. По документации проверь ссылки и команды, которые изменила правка.
- Проверяй нормальный вход в изменённый модуль. Если меняется контракт или исправляется регрессия, выбери проверку, которая выявляет конкретный сбой. Сообщи фактически выполненные проверки и причины пропусков.
- Используй SSH для `origin`. `main` служит источником выпуска. Коммит, push и деплой делай в рамках поручения пользователя.
- В README оставляй описание для человека. Инструкции, рабочие команды и границы модулей описывай в `AGENTS.md`; процедуры помещай в навыки.
- Требования, материалы трека и отчёты веди в `docs/`. В модульных инструкциях давай ссылки на эти документы.
